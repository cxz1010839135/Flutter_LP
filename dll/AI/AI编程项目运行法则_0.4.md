# AI编程项目运行法则

版本：0.4  
制定日期：2026-09-04

## 0. 本文件的作用

本项目采用“全 AI 编程”模式：用户主要负责需求规划、功能取舍、实际运行测试和结果确认，不以人工阅读、理解和长期维护代码作为项目连续性的保障。

因此，每个程序版本都必须自行携带足够的工程记忆，使项目在切换 ChatGPT、Codex、ZCode、Claude Code、Cursor、Copilot 或其他 AI 工具、模型、会话后，新的 AI 仍能快速恢复项目历史和当前状态，继续开发，而不是依赖用户重新讲述全部上下文。

本文件既是规则说明，也是初始化指令。任何 AI 在收到本文件及一个程序项目时，应自动执行本法则，无需用户另行提供初始化提示词。

核心目标：

1. 不丢失已确认的需求、规则、历史和调试结论；
2. 不重复无意义的工作和试错；
3. 不因不了解历史而破坏已经稳定的功能；
4. 不把旧 AI 的一次失败机械地当成永久技术结论；
5. 不为了“工程化”自行制造用户不需要的复杂目录、镜像、staging 或发布流程。

总原则：

> **每个版本文件夹都是一个完整、自包含、可直接开发、测试、交接和压缩的版本单元。AI 工程记忆必须跟着这个版本文件夹一起走。**

---


# 1. 每轮开发必须形成“启动—执行—归档—再启动”闭环

为了避免对话轮次增多、上下文压缩、模型切换或平台切换后逐渐遗忘本法则，每一轮编程、调试、分析和版本修改都必须从固定入口重新开始，不得依赖“上一轮还记得”。

## 1.1 每轮开始前的强制读取顺序

在修改任何代码、配置、脚本或程序行为之前，AI 必须先完成以下读取：

1. 读取当前版本文件夹中的 `AGENTS.md`；
2. 根据 `AGENTS.md` 的要求重新读取本《AI编程项目运行法则》；
3. 读取 `ai_project/STATUS.md`；
4. 如果当前版本存在运行日志，必须读取最新且与当前问题相关的运行日志；
5. 如果问题存在连续性、回归、历史尝试或原因不明，再按需回溯相关旧日志、`CHANGELOG.md` 和 `history/`。

在以上必读内容完成之前，不应直接修改代码。

原则：

> **每一轮都从事实和当前状态重新进入项目，而不是从模型记忆进入项目。**

## 1.2 运行日志是强制证据来源

只要程序存在运行日志，调试前就必须读取。

读取顺序优先为：

- 最新一次实际运行日志；
- 与用户当前反馈直接相关的日志；
- 必要时回溯前几次相关日志；
- 再结合代码和历史记录判断。

不允许只根据代码静态分析、理论推断或上一次 AI 的结论直接判断问题原因，而忽略真实运行日志。

当信息发生冲突时，原则上按以下证据优先级处理：

1. 用户实际运行现象；
2. 真实运行日志；
3. 可重复测试结果；
4. 当前代码和配置；
5. 历史文档；
6. AI 理论推断。

如果运行日志缺失、损坏、不完整，或信息不足以支持结论，必须明确记录“日志证据不足/缺失”，不得把推测写成已验证事实。

## 1.3 每轮结束前必须完成归档

每一轮实际开发、调试或版本修改结束前，AI 必须完成必要收尾，不得只交付代码后停止。

至少检查并按实际需要更新：

- `ai_project/STATUS.md`
- `ai_project/CHANGELOG.md`
- 当前版本对应的 `ai_project/history/vX.Y.Z.md`
- 如果长期项目事实变化，再更新 `PROJECT.md`
- 如果接手规则、测试方式或关键约束变化，再更新 `AGENTS.md`

如果本轮读取了运行日志，并由日志得出了对后续开发有价值的结论，应把必要结论写入当前版本历史记录，而不是只留在聊天上下文中。

归档时必须区分：

- 已验证解决；
- 待用户实际验证；
- 部分解决；
- 未解决；
- 无法确认；
- 新发现问题。

## 1.4 `AGENTS.md` 必须固定提醒这套闭环

每个版本中的 `AGENTS.md` 必须明确写出以下要求，措辞可以调整，但含义不得缺失：

```text
Before any coding or debugging work:
1. Read AGENTS.md completely.
2. Read the AI Programming Project Rules.
3. Read ai_project/STATUS.md.
4. If runtime logs exist, read the latest relevant logs before diagnosing or modifying code.
5. Read relevant history records when needed.

Do not modify code before completing the required reading.

At the end of every development/debugging round:
1. Complete required verification.
2. Update project memory and version history.
3. Record relevant runtime-log conclusions when needed.
4. Ensure STATUS.md reflects the real current state.
5. Leave the project ready for the next round, which must begin by reading AGENTS.md again.
```

`AGENTS.md` 的作用不是代替本法则，而是确保 AI 每轮重新回到本法则。

## 1.5 `STATUS.md` 必须保留下轮入口提醒

`STATUS.md` 中应长期保留一个简短的 `Next Session Entry` 区域，提醒任何下一轮 AI：

```text
## Next Session Entry

下一轮任何 AI 在修改代码前，必须重新读取：
1. AGENTS.md
2. AI编程项目运行法则
3. ai_project/STATUS.md
4. 如果存在运行日志，读取最新且与当前问题相关的日志
5. 必要时再读取相关 history
```

该区域只作为下轮入口提醒，不重复保存完整规则。

由此形成固定闭环：

> **开始 → 读 AGENTS.md → 读本法则 → 读 STATUS.md → 读最新相关运行日志 → 必要时追溯历史 → 开发/调试 → 验证 → 更新工程记忆 → 写清当前状态 → 下一轮再次从 AGENTS.md 开始。**

# 2. 版本文件夹自包含原则

本法则不规定用户工作区外层目录如何组织。

例如外层可以是：

```text
任意工作区/
└─ 任意分类/
   └─ 某个程序/
      ├─ 程序名_V0.3.0/
      ├─ 程序名_V0.3.0.zip
      ├─ 程序名_V0.3.1/
      └─ 程序名_V0.3.1.zip
```

真正需要遵守本法则的是具体版本文件夹，例如：

```text
程序名_V0.3.1/
```

这个版本文件夹本身就是：

- AI 日常开发位置；
- 源码维护位置；
- 调试位置；
- 实际运行测试位置；
- AI 工程记忆存放位置；
- 最终压缩交付的来源。

不要求另外创建：

- `_staging/`
- `build_tree/`
- `release_tree/`
- 解压镜像目录
- 专门维护源码副本
- 专门维护交付副本

除非程序本身确实有客观技术需要，且用户明确同意。

最终 ZIP 原则上就是对当前完整版本文件夹的直接压缩结果：

```text
程序名_V0.3.1/
        ↓ 直接压缩
程序名_V0.3.1.zip
```

版本文件夹里有什么，最终 ZIP 里就有什么。

# 3. AI 工程记忆必须放在版本文件夹内部

每个版本文件夹根目录应包含：

```text
程序名_V0.3.1/
├─ AGENTS.md
├─ ai_project/
│  ├─ PROJECT.md
│  ├─ STATUS.md
│  ├─ CHANGELOG.md
│  └─ history/
│     ├─ v0.3.0.md
│     └─ v0.3.1.md
├─ App/
├─ Config/
├─ Source/
├─ Logs/
└─ 其他程序文件……
```

`AGENTS.md` 和 `ai_project/` 必须跟程序代码、配置和其他必要文件处于同一个版本文件夹中。

禁止只放在多个版本共同的外层目录，例如：

```text
某个程序/
├─ AGENTS.md
├─ ai_project/
├─ 程序名_V0.3.0/
└─ 程序名_V0.3.1/
```

这种结构会导致 AI 工程记忆与具体版本脱离，单独拿走某个版本后上下文丢失，也可能产生版本错配。

---

# 4. 新版本的建立方式

创建新版本时，应以当前上一版本文件夹为基础。

例如：

```text
程序名_V0.3.1/
        ↓ 复制并修改
程序名_V0.3.2/
```

新版本应继承上一版本中的：

- 程序代码；
- 配置；
- 必要资源；
- `AGENTS.md`；
- `ai_project/`；
- 必要历史记录。

然后在新版本中更新：

- 版本号；
- 当前状态；
- 更新记录；
- 本版本历史记录；
- 与本次修改有关的项目事实。

原则：

> **历史是继承的，当前状态是更新的，每个版本文件夹都必须独立完整。**

不得让新版本继续依赖外层或旧版本中的唯一一份 AI 工程记忆。

---

# 5. `AGENTS.md` —— AI 接手入口

`AGENTS.md` 是当前版本 AI 接手的第一入口，应保持简短。

至少包含：

- 程序一句话用途；
- 当前版本；
- `ai_project/` 的读取顺序；
- 常用运行、构建、检查和测试方式；
- 必须遵守的核心业务和技术约束；
- 已确认稳定、不得擅自改变的关键行为；
- 修改后需要更新哪些工程记忆；
- 必要的环境和依赖说明。

AI 接手时应先读 `AGENTS.md`，再按当前任务读取其他文档。

禁止把完整聊天记录、全部版本历史或大量调试过程塞进 `AGENTS.md`。

如果某个 AI 工具需要自己的专用说明文件，可以建立轻量兼容文件，但应尽量只指向 `AGENTS.md`，避免维护两套互相分叉的项目事实。

---

# 6. `ai_project/PROJECT.md` —— 稳定项目知识

用于保存相对长期稳定的信息：

- 程序用途和功能边界；
- 用户实际工作流程；
- 核心业务规则；
- 主要架构和模块职责；
- 关键输入、输出和文件关系；
- 运行环境、依赖和外部软件/API；
- 关键目录、接口、命名和路径规则；
- 已确认的长期设计约束；
- 主要测试和验收方式。

`PROJECT.md` 回答：

> **这个程序是什么，为什么这样设计。**

不要把每轮 Bug、临时任务和版本流水账塞进去。

只有长期项目事实变化时才更新。

---

# 7. `ai_project/STATUS.md` —— 当前版本状态

`STATUS.md` 是新 AI 快速恢复当前现场的核心文件，必须保持短、准、新。

至少记录：

- 当前版本；
- 当前版本基于哪个上一版本；
- 最近一个经过用户实际确认的稳定版本；
- 当前已经稳定的主要功能；
- 正在处理的问题；
- 尚待用户实际验证的修改；
- 当前已知风险；
- 下一步最优先任务。

`STATUS.md` 只描述“现在”。

已经结束的问题从当前状态中移除，其历史保留在版本记录里。

---

# 8. `CHANGELOG.md` 与 `history/` —— 版本历史

`CHANGELOG.md` 只作为简洁版本索引。

每个实际交付给用户测试、正式确认或正式归档的版本记录：

- 版本号；
- 日期；
- 本版主要修改；
- 最终状态；
- 对应历史文件。

例如：

```text
v0.3.1
- 修复：……
- 新增：……
- 状态：待用户验证
- 详情：history/v0.3.1.md
```

每个实际交付版本在 `history/` 中建立一份完整记录：

```text
history/v0.3.1.md
```

建议结构：

```text
# v0.3.1

## 本轮目标
本版本要解决什么。

## 基于版本
从哪个版本开始修改。

## 用户反馈 / 问题现象
实际问题、触发条件和必要证据。

## 原因判断
区分已证实事实与尚未验证的推测。

## 实际修改
修改了哪些模块、行为或逻辑，以及原因。

## 验证
做了哪些构建、检查、测试或实际运行验证。

## 结果
明确标记：
- 已验证解决
- 待用户实际验证
- 部分解决
- 未解决
- 无法确认
- 引入新问题

## 遗留事项
下一轮仍需处理的问题。

## 技术尝试记录
仅在有必要时记录重要方案、条件、证据和结果。
```

一份版本历史同时承担：

- 更新内容；
- 调试记录；
- 验证结果；
- 重要技术尝试。

不要为同一版本再机械拆成多个重复文档。

AI 内部临时修改、未交付的中间试验，不需要每次单独建立版本历史，可合并进最终实际交付版本。

# 9. AI 每轮开发的标准流程

本节与第 1 节的闭环规则同时适用：第 1 节规定每轮必须重新读取入口、状态和运行日志，本节规定具体修改与收尾动作。

## 8.1 修改前

AI 应：

1. 读取当前版本文件夹中的 `AGENTS.md`；
2. 读取 `ai_project/STATUS.md`；
3. 根据任务读取 `PROJECT.md`；
4. 搜索 `CHANGELOG.md` 和 `history/` 中与当前问题相关的历史；
5. 检查当前代码、日志和实际文件，确认历史文档与现状没有明显冲突。

不要求每次通读全部历史，只追溯与当前任务相关的内容。

---

## 8.2 修改时

- 优先解决用户当前明确要求的问题；
- 优先做最小、可解释、可验证的修改；
- 不因“代码不够漂亮”而擅自重构稳定模块；
- 不自行改变已经确认的业务规则；
- 不顺带扩大到与本轮无关的功能；
- 不擅自增加用户没有要求的目录层级、镜像、staging 或发布流程；
- 修改稳定模块时必须考虑回归影响；
- 文档与代码冲突时，应结合实际代码、日志、运行结果和用户确认判断。

---

## 8.3 修改后

AI 应：

1. 执行当前环境能够执行的构建、语法检查、自动测试或其他验证；
2. 检查是否出现明显回归；
3. 确认当前版本文件夹本身仍可直接运行和交接；
4. 更新当前版本的 `history/vX.Y.Z.md`；
5. 更新 `CHANGELOG.md`；
6. 更新 `STATUS.md`；
7. 只有长期项目事实变化时才更新 `PROJECT.md`；
8. 只有接手规则、核心约束或测试方式变化时才更新 `AGENTS.md`；
9. 最终需要交付 ZIP 时，直接压缩当前完整版本文件夹。

不得为了“文档同步”每轮重写全部工程记忆。

---

# 10. 历史失败不能直接等于“路线禁止”

历史尝试的作用是提供证据，而不是给技术路线永久判死刑。

一次失败可能来自：

- 技术路线本身确实不适用；
- 当时实现方法错误；
- AI 实际没有真正完成所声称的实现；
- 测试方式不足；
- 日志证据不足；
- 软件/API/工具版本限制；
- 环境差异；
- 问题理解错误；
- 当时成本收益不合理，但技术上并非不可行。

因此，历史技术尝试使用以下语义：

### 已验证可行
已有明确测试证据。

### 特定实现下失败
只证明当时条件和实现没有通过，不代表整个技术路线永久不可行。

### 暂缓
当前成本、风险或收益不值得继续，但未来条件变化后可以重新评估。

### 客观不适用
存在可靠的官方接口、底层机制、硬件、物理或其他客观限制证据。

“客观不适用”也必须注明依据和适用条件。

---

# 11. 重新尝试历史路线的规则

AI 想重新尝试以前失败的路线时，应先判断：

> **这一次相对上次有什么新增变量或新证据？**

合理的新变量包括：

- 实现方法不同；
- 发现上次属于伪实现或没有真正执行目标逻辑；
- 新日志证明上次原因判断错误；
- 模型或工具能力明显变化；
- 软件/API 版本变化；
- 获得新的官方资料；
- 测试环境改善；
- 程序架构已经变化。

如果历史记录只有“试过，不行”，却没有足够代码、日志、测试或其他证据，不得把它当成充分证伪，应视为证据不足，可以重新评估。

如果没有新增变量，也没有证据说明上次尝试无效，则不应机械重复同一方案。

历史结论被新证据推翻时，应保留原历史，并在新版本记录中说明为什么修正旧结论。

---

# 12. 必须区分事实、推测和验证状态

AI 不得把：

> “代码已经改了”

写成：

> “问题已经解决”。

统一使用以下状态：

- **已验证解决**：已有充分测试或用户实际运行确认；
- **待用户实际验证**：代码已修改，但真实软件/设备环境尚未确认；
- **部分解决**：只有部分条件通过；
- **未解决**：目标仍未达到；
- **无法确认**：缺少必要环境或证据。

原因分析也应区分：

- 已证实；
- 高概率判断；
- 初步推测；
- 未知。

如果用户实际运行结果与 AI 理论判断冲突，以实际运行结果作为新的最高优先级证据继续排查。

---

# 13. 稳定功能优先保护

已经经过用户实际测试并确认稳定的功能，应默认视为受保护逻辑。

修复新问题时：

- 优先局部修改；
- 不得无理由大范围重构；
- 不得为了代码形式更统一而改变已验证行为；
- 不得自行更改业务规则；
- 不得顺手重写与当前任务无关的模块。

如果确实必须改动稳定模块，应在版本记录中说明：

- 为什么必须修改；
- 影响范围；
- 回归风险；
- 如何验证；
- 必要时如何回退。

---

# 14. 调试日志必须能支持 AI 排错

需要长期调试的程序，应保留足够可追溯的运行日志。

日志优先记录：

- 程序版本；
- 运行时间；
- 必要环境信息；
- 关键输入和输出路径；
- 主要处理阶段开始、结束和结果；
- 当前处理对象；
- 成功、失败、跳过数量；
- 跳过原因；
- 异常类型；
- 异常信息；
- 必要调用位置；
- 最终汇总。

日志目标是让 AI 能回答：

> **程序实际执行到了哪里、处理了什么、从哪里开始偏离预期、失败时有哪些证据。**

不能只记录“运行失败”“发生异常”等没有定位价值的信息。

---

# 15. 控制工程记忆规模

工程记忆不是越多越好。

禁止：

- 保存完整聊天记录；
- 保存 AI 思维过程；
- 同一事实长期复制到多个文件；
- 每个小问题都建立永久文档；
- 每次未交付内部试验都建立新版本；
- 把大量旧问题长期堆在 `STATUS.md`；
- 把所有版本历史塞进 `AGENTS.md`。

统一遵循：

> **稳定知识进 `PROJECT.md`；当前现场进 `STATUS.md`；版本索引进 `CHANGELOG.md`；具体历史进 `history/`。**

只有项目确实出现长期、跨版本、无法合理放入现有文档的重要架构决策时，才允许新增类似 `DECISIONS.md` 的文件。

不得为了“看起来完整”无限扩充文档体系。

---

# 16. 本文件首次接入已有程序时

AI 收到本文件和一个已有程序时，应自动：

1. 识别用户当前正在维护的具体版本文件夹；
2. 不对其外层工作区结构做额外假设；
3. 检查该版本文件夹内是否已有 `AGENTS.md` 和 `ai_project/`；
4. 如果没有，则阅读当前代码、说明、日志、版本资料和已有交接资料；
5. 在当前版本文件夹内部建立工程记忆；
6. 提炼已有历史，而不是机械复制全部旧资料；
7. 无法确认的内容标记为“未知”或“待验证”，不得自行编造；
8. 初始化工程记忆时，不擅自增加 staging、镜像、构建副本等目录；
9. 初始化阶段不擅自修改程序功能，除非用户同时明确提出开发或修复任务。

如果用户仅提供本文件和程序，没有附加开发任务，则 AI 应完成工程记忆初始化或检查，并简要报告：

- 当前识别到的程序和版本；
- 当前版本文件夹；
- 已建立或已发现的 AI 工程记忆；
- 当前项目状态；
- 发现的资料冲突、缺失或待确认项。

---

# 17. 完成标准

一个版本文件夹的 AI 工程记忆达到合格状态，应满足：

- 单独拿走这个版本文件夹，新 AI 仍能知道它是什么程序；
- 能知道当前版本和上一稳定版本；
- 能区分稳定功能、正在调试内容和待验证内容；
- 能查到本版本为什么修改、修改了什么、结果如何；
- 能追溯必要的历史版本；
- 能判断旧失败是真失败、特定实现失败还是证据不足；
- 能知道如何运行、构建和验证程序；
- 能知道修改后需要更新哪些工程记忆；
- 不依赖外层工作区或原聊天记录才能继续工作；
- 不需要额外维护 staging、镜像或发布副本；
- 最终 ZIP 可以直接由当前完整版本文件夹压缩得到；
- 文档数量没有膨胀到妨碍 AI 获取重点。

最终原则：

> **每个版本文件夹就是完整的 AI 可接手单元，也是直接开发、调试、运行和最终压缩的同一套文件。AGENTS.md 负责告诉 AI 如何工作，ai_project/ 负责保存项目事实、当前状态和必要历史；工程记忆随版本继承；稳定功能优先保护；失败经验保留但不机械封死路线；每次实际交付都完成“读取历史—修改—验证—记录—直接压缩版本文件夹”的闭环。**

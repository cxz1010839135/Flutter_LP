# v2.2.3

## 本轮目标

新增点位库文件仓功能（用户需求原话）：

- 保存点位库：把当前点位库保存到驱控（图二目录）下新增的 `pointHome` 文件夹，目录不存在则新建，名称可自定义，默认后缀 `.rpt4`。
- 导入：可从「内存卡（驱控目录）」或「电脑/安卓本地目录」两种来源导入，只找 `.rpt4` 后缀文件。

用户在需求澄清中确认的三点：

1. pointHome 位置：`/home/llmachine/` 下，即 `/home/llmachine/pointHome/`；
2. 入口：点位页**底栏**（不放右侧操作栏、不放顶栏）；
3. 导入语义：**仅存入 pointHome，不改变驱控当前点位库**。

## 基于版本

`2.2.2+7`（v2.2.1 / v2.2.2 无 history 条目，未追溯）。

## 后续轮次：导入速度慢——缩短刷新命令超时 + 耗时日志（2026-10-26 第四轮）

### 用户反馈 / 问题现象

用户反馈「现在导入速度很慢，能不能加快」。

### 慢点定位（代码事实）

导入流程（本地源）：读文件 → 写中转临时 → 上传 `para/rbt_Point.rpt4` → `refreshPointLibrary` → 表格刷新。各步耗时特征：

- **上传**：`postRawBody` 对小文件（<1MB，`.rpt4` 仅数 KB）设 `ackOptional=true`、`smallUploadAckWait=500ms`，最多等 500ms 即返回，不慢。
- **刷新（主因）**：`refreshPointLibRaw` → `robotCmdRaw` → `postCommand` → `_postViaSocket`，用默认 `ioTimeout=45s`、`ackOptional=false`。而驱控 HTTP 服务实测响应偏慢（`robotGetCurState` 约 30s 才回空 body），刷新命令会阻塞到驱控应答或 45s 超时。
- **内存卡源下载**：`downloadRobotFileBytes` → `postCommandBytes` 用 `ioLimit=120s`，驱控响应慢时同样会等，但不可避免（无远程 cp 命令，只能下载再上传）。

### 实际修改

- `lib/network/api/robot_http_api_mixin.dart`：`robotCmdRaw` 增加可选 `ioTimeoutOverride` / `connectTimeoutOverride` 参数（对齐 `robotCmd` 已有 `fastTimeout` 模式）。
- `lib/network/api/robot_http_points.dart`：`refreshPointLibRaw` 默认 `ioTimeout=8s`、`connectTimeout=5s`。理由：文件已写入 `para/rbt_Point.rpt4`，表格有本地解析兜底，刷新仅给驱控一个重载信号，不必等满 45s；驱控若 8s 内不应答，按既有逻辑视为「文件已写入、刷新未确认」并提示用户重启。
- `lib/features/point_library/point_library_file_io.dart`：`importAsCurrentPointLibrary` 各步骤（读取/写入/刷新）加 `Stopwatch` 耗时日志，状态消息带耗时与字节数，末尾输出总耗时，便于用户复测时定位残余慢点。

### 验证

- `flutter analyze`（3 个改动文件）通过，无新增问题；
- `flutter test` 29/30（`widget_test` 存量失败），解析器 3 用例全过。

### 结果

- 刷新命令等待时间从「驱控应答或 45s」降为「驱控应答或 8s」，本地源导入理论上从可能 30s+ 降到 8s 以内（若驱控在 8s 内应答则更快）。
- **待用户复测**：导入状态栏各步耗时日志（读取/写入/刷新/总耗时），确认刷新是否从 30s 降到 8s 内；若内存卡源仍慢（下载耗时），属驱控 HTTP 响应慢，需另寻方案（如固件侧加 cp 命令）。

## 后续轮次：导入后重启软件点库没变——上传回读校验 + 逐点 updatePoint 兜底（2026-10-26 第五轮）

### 用户反馈 / 问题现象

用户反馈「好像没有完全导入，重启软件回来没有变化」。即导入时表格刷新了（本地解析），但重启软件重连驱控后，点库仍是旧的。

### 原因判断

1. **刷新命令不生效**：日志（13:36:08）显示 `refreshPointLibrary` 返回"连接超时"——该命令固件可能未实现或响应极慢（>8s），驱控内存点库未从 `rbt_Point.rpt4` 重载。连接时驱控返回的是内存点库，故重连后仍是旧点位。
2. **上传是否真覆盖了文件未验证**：`postFileWithTagForRestore` 对空 body 不抛错，仅凭应答无法判断覆盖是否成功。

### 实际修改

- `point_library_file_io.dart` `importAsCurrentPointLibrary`：
  1. **上传后回读校验**：上传 `para/rbt_Point.rpt4` 后立即下载回来逐字节对比，确认内容真的被覆盖；不一致则抛错中止（不再误报"写入成功"）。
  2. **refresh 超时从 8s 调到 20s**：给驱控更多响应时间。
  3. **逐点 updatePoint 兜底**：若 `refreshPointLibrary` 仍未应答，逐点调用 `updatePoint(index, label, describe, joints, refresh=true)` 直接修改驱控内存点库并落盘——不依赖 `refreshPointLibrary`，确保重连后点库已更新。
  4. `PointImportResult` 新增 `uploadVerified` 字段。
- `robot_http_points.dart` `refreshPointLibRaw`：默认超时保持 8s，导入场景显式传 20s。

### 验证

- `flutter analyze lib/` 无新增问题（8 条历史 info）；
- `flutter test` 29/30（`widget_test` 存量失败），解析器 3 用例全过。

### 风险与未证实项

- **`updatePoint` 对不存在的点位是否能创建（upsert）**：若驱控要求点位先存在，部分点位会失败（日志会列出失败索引）。届时需改为 `addPoint` + `updatePoint` 两步。
- **多余点位未删除**：若导入文件点位比当前点库少，多余点位仍保留（用户可手动删）。若需完全替换，需追加逐点 deletePoint。
- **逐点 updatePoint 较慢**：每个点位一次 HTTP 往返，点位多时导入耗时增加。

### 结果

- 上传覆盖真实性：**可验证**（回读校验，不一致即报错）。
- 驱控内存点库更新：**双保险**——`refreshPointLibrary` 成功则一次完成；失败则逐点 updatePoint 兜底。
- **待用户复测**：① 状态栏看"校验通过/未通过"确认文件是否覆盖；② 刷新失败时看"逐点写入"成功数；③ 重启软件后点库是否变为导入内容。

## 后续轮次：新产物复测 3/11 成功——updatePoint 非 upsert 证实，改两步写入 + 删多余点（2026-10-26 第七轮）

### 用户反馈 / 问题现象

用户用 13:58 重编译的 Debug 产物复测（日志 14:00:40 / 14:01:36 / 14:03:19 三次导入，均走完新链路：回读校验通过 → refresh 连接超时 → 逐点兜底），并发截图：**逐点写入 293ms 内 3/11 成功，失败 8 个点位**；导入后表格只显示 3 个点（即成功的那几个，来自固件 updatePoint 响应携带的点库数据）。

### 诊断结论（已证实）

1. **updatePoint 非 upsert**：仅对驱控内存中**已存在**的点位生效；不存在的点位约 30ms 即被拒（响应极快，说明驱控 HTTP 服务本身不慢——refreshPointLibrary 的不应答是该命令自身问题）。失败的全是内存中不存在的点位，成功的恰是已存在的。
2. **updatePoint 响应携带最新点库数据**（表格显示的 3 个点即来自 `applyFromResponseRoot`），可用于导入后的表格刷新。
3. 上一轮 `catch (_)` 吞掉了全部错误详情，日志无法还原失败原因（中间 onStatus 走 info 级不落盘）——本轮修复。

### 实际修改（`point_library_file_io.dart` + `point_library_page.dart`）

1. **两步 upsert**：`updatePoint` 失败 → `addPoint`（新建，关节值为 0）→ 再 `updatePoint` 写关节值。
2. **删除多余点位**：内存中不在导入文件内的点位逐个 `deletePoint`（用连接时快照的 label/joints），对齐确认弹窗承诺的「覆盖驱控当前点位库」语义。
3. **refresh 语义收紧**：只有**带回点库数据**的应答才视为生效（空 body 已证实不重载内存）；超时从 20s 降回默认 8s（反正等不到有用应答，别卡导入）。
4. **错误详情落日志**：失败原因逐点捕获（updatePoint 与 addPoint 两步的错误都记），去重最多 3 条写入 `PointImportResult.errorDetail`；UI 的 WARN 消息带失败点位列表 + 原因（warning 自动同步到 `app_*.log`，不再丢诊断信息）。
5. **空文件防线**：解析出 0 个点位直接抛错中止，避免「导入空文件 → 删光内存点库」。
6. `refreshed` 语义 = refresh 生效 或 逐点写入+删除全部成功；`PointImportResult` 新增 `upsertFailures` / `deleteFailures` / `errorDetail`。

### 风险与未证实项

- **addPoint 是否遵守请求的 pointindex**：若固件忽略序号自动分配，两步写入后 updatePoint 仍会失败——错误详情会显示（日志可判）。
- **addPoint 对空名称是否接受**：导入文件大量空名称点位，若被拒同样体现在错误详情。
